# ADR-0005 — Internal API contract for Phase 3

**Status:** Proposed — implemented and tested locally.
**Date:** 2026-11-13
**Owners:** backend-architect, product-architect
**Related:** `docs/architecture/api-design.md`

## Context

The platform needs a stable internal REST contract that exposes stored football data without
leaking provider payloads or provider credentials. Phase 3 has no authentication, no user
accounts, and no write surface. The API must not trigger external provider calls per request.

## Decision

- Base path `/api/v1`; the version is part of the path.
- The API reads only from the platform database. Provider access happens exclusively in the
  sync worker.
- Read-only endpoints only in Phase 3. Manual synchronisation is a CLI operation, not an
  unauthenticated write endpoint.
- JSON responses use camel-free `snake_case` fields (the storage naming is not exposed; the
  schemas are explicit).
- List endpoints use page/page-size pagination with a deterministic sort and return
  `{items, page, page_size, total, has_next}`.
- Errors use one envelope: `{"error": {"code", "message", "details", "request_id"}}`.
  Validation failures return 422, missing resources 404, unsupported operations 405/501, and
  unexpected failures a generic 500 with no internal detail.
- `GET /health` is a liveness check; `GET /api/v1/health` reports database connectivity and
  last successful synchronisation. Readiness is separate from liveness.
- OpenAPI is generated by FastAPI and available at `/docs` and `/openapi.json` when
  `API_DOCS_ENABLED=true`.

## Endpoints in Phase 3

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/health` | process liveness |
| GET | `/api/v1/health` | DB readiness + sync freshness |
| GET | `/api/v1/fixtures` | filtered, paginated fixtures |
| GET | `/api/v1/fixtures/today` | fixtures for a UTC or IANA-zoned day |
| GET | `/api/v1/fixtures/{match_id}` | match detail |
| GET | `/api/v1/fixtures/{match_id}/statistics` | available team statistics |
| GET | `/api/v1/competitions` | competitions |
| GET | `/api/v1/competitions/{competition_id}` | competition detail |
| GET | `/api/v1/seasons` | seasons, filterable by competition |
| GET | `/api/v1/teams` | teams, filterable and searchable |
| GET | `/api/v1/teams/{team_id}` | team detail |
| GET | `/api/v1/teams/{team_id}/matches` | team fixture history |
| GET | `/api/v1/sync/runs` | recent sync runs |
| GET | `/api/v1/sync/status` | last success/failure and data freshness |

## Alternatives considered

- **No version prefix.** Rejected: the contract will change as the model grows.
- **Expose provider-shaped JSON.** Rejected: it couples clients to a vendor and leaks fields
  the platform does not validate.
- **Envelope every response in `{data: ...}`.** Rejected as unnecessary; lists already have a
  pagination envelope and errors are distinct.
- **Cursor pagination.** Not justified at Phase 3 volume and harder to make stable across
  updates. Page-based pagination with a deterministic sort is sufficient; revisit on measured
  deep-page cost.
- **POST `/sync` endpoint.** Rejected until authentication and authorisation exist.

## Consequences

- Every endpoint has an explicit Pydantic response model; provider DTOs are never returned.
- Query filters are allowlisted; unknown filters are rejected by FastAPI.
- `GET /fixtures` with no narrowing filter defaults to a bounded window (today through
  `+7` days) to avoid unbounded scans.
- Missing statistics return `200` with `available: false`, because "no statistics" is a data
  state, not a missing match.

## Risks

- Page-based pagination can drift if data changes between pages. Acceptable for read-only
  reference data; documented.
- Without authentication, the API must not be exposed publicly in Phase 3. Deployment docs
  state this explicitly.
- The error envelope is a project convention, not a standard; clients must follow the
  documented schema.
